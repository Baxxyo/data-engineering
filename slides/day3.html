01
The problem

A folder of Parquet files is not a table

No atomic writes. A job dies after writing 40 of 100 files: readers see half a load.
No updates or deletes. One refunded order or one erasure request means rewriting whole files by hand.
No safe concurrency. Two writers, one folder: last one wins, silently.
Slow planning. Listing 100,000 objects on S3 takes longer than reading the data you need.
Schema by convention. A renamed column? Hope every reader got the memo.
Hive-style tables (2010s) added a metastore pointing at folders, plus dt=2026-09-23/ partitions. Better, but the folder was still the truth.
Table formats (Iceberg, Delta Lake, Hudi) move the truth into metadata files: an explicit list of which data files make up the table, at each version. Everything else follows from that.

Apache Iceberg

The metadata tree

  • Catalog: maps a table name to its current metadata file. A commit is one atomic pointer swap.
  • metadata.json: schemas, partition specs, the list of snapshots. A new file per commit.
  • Manifest list: the manifests of one snapshot, with partition ranges to skip whole manifests.
  • Manifests: data files with per-column stats, to skip files.
  • Readers follow pointers; they never list directories.
Snapshots

Every write is a new snapshot; old ones stay readable

orders.append(batch1)          # snapshot 1
orders.append(batch2)          # snapshot 2
orders.upsert(refunds, join_cols=["order_id"])
orders.delete("customer_id = 105495")

for s in orders.snapshots():   # time travel
    t = orders.scan(snapshot_id=s.snapshot_id)
    print(s.summary.operation, t.to_arrow().num_rows)
# append 1868 · append 4701 · overwrite 4696
# append 4701 · overwrite 4700
Optimistic concurrency. Writers prepare new files, then try to swap the catalog pointer. If someone else committed first, they re-check for conflicts and retry. No locks while writing.
Time travel answers "what did the table say when the dashboard broke?" and pins reproducible ML training sets.
But: deleted rows live on in old snapshots. The PDPL right to erasure needs snapshot expiry too (Lab 3.1 stretch, Lab 4.3).
Row-level changes

Copy-on-write vs. merge-on-read

Copy-on-write

Rewrite every data file that contains a changed row.

  • ✓ reads are as fast as ever
  • ✗ one updated row rewrites a 512 MB file
  • Good for: rare, large batch changes

Merge-on-read

Write small delete files (or deletion vectors) next to the data; readers merge them in.

  • ✓ cheap, fast writes (CDC, streaming upserts)
  • ✗ reads slow down until compaction
  • Good for: frequent small changes
Iceberg v3 (2025) replaced position-delete files with compact deletion vectors (shared with Delta), and added a VARIANT type for semi-structured JSON and row lineage for incremental processing.
Evolution

Change the schema and the partitioning without rewriting data

# hidden partitioning: derived from a column
with orders.update_spec() as spec:
    spec.add_field("created_at", DayTransform(),
                   "created_day")

# months later: new column, new layout
with orders.update_schema() as upd:
    upd.add_column("channel", StringType())
with orders.update_spec() as spec:
    spec.remove_field("created_day")
    spec.add_field("created_at", MonthTransform(),
                   "created_month")
  • Columns are tracked by ID, not name: rename, reorder, add and drop safely.
  • Hidden partitioning: queries filter on created_at; they never mention created_day, so no one scans the whole table by forgetting the partition column.
  • Old files keep the old spec, new files use the new one; the planner handles both. In Lab 3.1: 8 daily files and 1 monthly file, one table.

Checkpoint

Spark and DuckDB both write to the same Iceberg table at the same moment. What happens?

The table is corrupted: one writer's files overwrite the other's
Both write their own files; the first to swap the catalog pointer wins, the second checks for conflicts and retries its commit
The second writer blocks until the first finishes writing its data files
B. Data files are never shared or modified, so writes don't collide. Only the commit (one pointer swap in the catalog) is serialized: optimistic concurrency.

Distributed processing with Spark

02
Do you need a cluster?

Scale up first; scale out when you must

One machine is enough for most tables: DuckDB and Polars handle hundreds of GB on a large VM, with no cluster to run.
Reach for Spark when a single job reads terabytes, the work must finish within a window one machine can't meet, or many teams share one platform.
You'll meet Spark anyway: Databricks, EMR, Dataproc, Microsoft Fabric and Glue all run it, and many existing pipelines are written in it.
Spark 4 (2025–26): ANSI SQL by default, a VARIANT type for JSON, Spark Connect (a thin client talking to a remote cluster), a Python data-source API, and Arrow everywhere between the JVM and Python.
Architecture

One driver, many executors

Driveryour program · builds and optimizes the plan · schedules tasks
→
Cluster managerYARN · Kubernetes · standalone · a managed service
→
ExecutorsJVM processes on worker nodes · run tasks · cache data

Job

One per action (count, write, collect).

Stage

A run of work with no shuffle. Each shuffle starts a new stage.

Task

One stage on one partition. Tasks run in parallel on executor cores.

In Lab 3.2 everything runs in one process (local[2]): driver and executors share your Colab VM. The code is identical on a 1,000-node cluster; only .master() changes.
Lazy evaluation

Transformations build a plan; actions run it

orders = spark.read.parquet("lake/orders")  # by order_date
national_day = orders.filter(
    (F.col("order_date") == "2026-09-23")
    & (F.col("status") == "delivered"))  # nothing runs
national_day.count()                         # action → 1 job
national_day.explain()
# FileScan parquet ...
#   PartitionFilters: [order_date = 2026-09-23]
#   PushedFilters: [EqualTo(status,delivered)]
  • Waiting lets Catalyst (the optimizer) see the whole pipeline: prune partitions, push filters, pick join strategies.
  • Narrow transformations (filter, select, withColumn) stay in one partition.
  • Wide ones (groupBy, join, orderBy, distinct) need rows from many partitions: a shuffle.
Shuffles

Every Exchange in the plan is a shuffle

HashAggregate(keys=[city, order_date], sum(...))
+- Exchange hashpartitioning(city, order_date, 8)
   +- HashAggregate(keys=[city, order_date], partial_sum)
      +- BroadcastHashJoin [store_id]
         :- BroadcastHashJoin [order_id]
         :  :- FileScan parquet order_items
         :  +- BroadcastExchange
         :     +- FileScan parquet orders
         +- BroadcastExchange
            +- FileScan parquet stores
  • A shuffle writes every row to local disk, sends it over the network to the executor that owns its key, and reads it back. It's where jobs spend time, memory, and fail.
  • Partial aggregation before the shuffle (above) shrinks what moves.
  • spark.sql.shuffle.partitions (default 200) sets the parallelism after a shuffle; AQE coalesces it at run time.
Joins

How Spark joins two tables

StrategyHowWhen
Broadcast hash joincopy the small side to every executor; no shuffle of the big sideone side < autoBroadcastJoinThreshold (10 MB default; often raised to ~100 MB)
Sort-merge joinshuffle both sides by key, sort, mergetwo large tables: the default
Shuffle hash joinshuffle both, hash the smaller side per partitionone side is medium-sized; AQE may choose it at run time
facts.join(F.broadcast(dim_store), "store_id")
Rule of thumb: broadcast dimensions, shuffle facts. Hint with F.broadcast() when Spark's size estimate is wrong; never broadcast something that doesn't fit in executor memory.
Skew

A job is as slow as its slowest task

task 1
30 s
task 2
33 s
task 3
29 s
task 4: Sep 23
40 min

Illustrative: partitioning by date puts all of National Day in one task.

AQE skew join (on by default): splits oversized partitions in sort-merge joins at run time.
Salting: add a random-ish key (order_id % 4), aggregate per (key, salt), then per key.
Fix the key: a better partition key, or handle the hot key separately (often NULL or "unknown").
Writing output

Each task writes a file into each folder it touches

# 8 tasks × 3 cities → 24 files
items_wide.write.partitionBy("city") \
    .parquet("out_naive")

# one task per city → 3 files
items_wide.repartition("city") \
    .write.partitionBy("city") \
    .parquet("out_tidy")
  • At scale: 1,000 tasks × 365 days = 365,000 files. That's the small-files problem from Day 1.
  • Fixes: repartition by the partition column, AQE's rebalance, or let the table format compact later (Session 4).
  • In production, write Iceberg or Delta tables, not bare Parquet: df.writeTo("cat.db.orders").append().

Do you need streaming?

Freshness is a requirement, not a default

~1 h

record-at-a-time
< 1 s

Data latency, log scale (illustrative). Cost and operational effort grow as you go down.

Stream when someone acts on the data within minutes: courier dispatch, fraud, stock-outs, a live SLA board.
Batch when people look at it the next morning: finance, most dashboards, model training.
Ask "what decision changes if this is 5 minutes old instead of 5 hours?"
The log

A topic is a set of append-only, partitioned logs

  • Partition = unit of order and parallelism. Same key → same partition → per-key order.
  • Offset = position in a partition. Consumers track their own; reading doesn't delete.
  • Consumer group: partitions are shared among its members; each group gets every record.
  • Kafka 4 runs on KRaft only (no ZooKeeper). Compatible: Redpanda, WarpStream, AutoMQ, cloud services (MSK, Event Hubs, Confluent Cloud).
Delivery guarantees

At-most-once, at-least-once, "exactly-once"

GuaranteeConsumer doesAfter a crash
At-most-oncecommit offsets, then processthe in-flight batch is lost
At-least-onceprocess, then commit offsetsthe in-flight batch is processed twice
Effectively-onceat-least-once + idempotent or transactional outputreplays have no visible effect
In Lab 3.3 one crash plus the phones' own retries over-count deliveries by 117. Counting each event_id once fixes both.
Idempotent sinks: MERGE on a key (Lab 1.4), upsert into Iceberg, or commit output and offsets in one transaction (Labs 3.3 ✱ and 3.4).
Two clocks

Event time vs. processing time

Event time: when it happened (the courier's phone). What the business means by "deliveries between 21:00 and 21:15".
Processing time: when the platform received it. Easy, but results change with network hiccups and replays.
And phones write event time in three formats: +03:00, Z and epoch millis. Parse first.

Grouping an endless stream

Tumbling

Fixed, non-overlapping: deliveries per 15 minutes.

[21:00, 21:15) [21:15, 21:30) …

Hopping / sliding

Fixed size, overlapping: orders in the last 15 minutes, every minute.

Checkpoint

Your consumer commits offsets before processing each batch. It crashes mid-batch. What happens?

The batch is processed twice after restart
The rest of that batch is never processed: data loss (at-most-once)
Nothing: Kafka re-sends uncommitted records automatically
B. The restart resumes after the committed offset, skipping what wasn't processed. Process first, commit after (at-least-once), and make processing idempotent.

Streaming jobs

Exactly-once into a table

Commit the data and the offset together

def commit_batch(tbl, rows, end_offset, batch_end):
    tbl.append(to_arrow(rows), snapshot_properties={
        "qafila.offset": str(end_offset),
        "qafila.batch_end": batch_end.isoformat()})

def committed_offset(tbl) -> int:
    for snap in reversed(tbl.snapshots()):
        off = snap.summary.additional_properties \
                  .get("qafila.offset")
        if off is not None:
            return int(off)
    return 0
One Iceberg commit = data + progress. There is no moment where one is saved and the other isn't, so a restart resumes exactly where the table says.
Producer duplicates still need a key: a bounded set of recent event_ids (Spark's dropDuplicatesWithinWatermark).

Compact: rewrite small files per partition (Spark rewrite_data_files, or managed: S3 Tables, Databricks, Snowflake).
Expire snapshots and remove orphan files: otherwise storage only grows.
Rewrite manifests and sort/cluster data for the common filters.
Maintenance commits can conflict with the streaming writer: schedule them on cold partitions (yesterday's), and let optimistic concurrency retry.
Architectures

Lambda vs. Kappa

Lambda

A batch layer recomputes the truth nightly; a speed layer gives approximate real-time results; queries merge both.

✗ two code paths for one metric, which drift apart

Kappa

One streaming path. To fix a bug or add a metric, replay the log through the new job.

✓ one code path · needs long retention and replayable sinks

The 2026 middle ground: stream into Iceberg (bronze), then run the same dbt models on a short schedule (every 5–15 min) with incremental reads. One code path, near-real-time, and late data simply lands in the next run.
