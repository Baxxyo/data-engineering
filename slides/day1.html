Architectures

Warehouse, lake, lakehouse

Data warehouse

Managed SQL engine with its own storage format. Strong governance and performance.

Snowflake, BigQuery, Redshift, Synapse

Data lake

Cheap object storage full of files (Parquet, JSON, CSV). Flexible, but "files are not tables": no transactions, no safe updates.

S3, ADLS, GCS, HDFS, MinIO

Lakehouse

Files on object storage plus an open table format (ACID, schema, time travel) plus a catalog. Many engines, one copy.

Iceberg, Delta Lake, Hudi, DuckLake

2026 reality: surveys still show warehouses as the most common setup (≈44%) with lakehouses (≈27%) and hybrids (≈12%) growing, and the major warehouses now read and write Iceberg. The debate is fading: learn the open table formats either way (Day 3).
Numbers are from Joe Reis's 2026 State of Data Engineering survey (≈1,100 respondents). Don't over-sell them: they are self-reported. The point is convergence on open formats.

Layers

Medallion layers: a contract between stages

Bronze · raw

  • Exactly what the source sent
  • Append-only, plus load metadata
  • Replayable history

Silver · staging

  • Typed, deduplicated, conformed
  • One row per entity or event
  • Bad rows quarantined

Gold · marts

  • Business-ready facts and dimensions
  • Metrics, aggregates, features
  • What dashboards and AI read
Names vary (raw / staging / marts in dbt, landing / curated / consumption elsewhere). What matters: each layer has a clear promise, and consumers only read the layer meant for them.

DuckDB: an analytical database in a library

import duckdb
con = duckdb.connect()            # in-memory; or "qafila.duckdb"

# Query files where they are: no load step
con.sql("""
  SELECT event_type, count(*) AS n
  FROM read_json_auto('data/raw/events/delivery_events.jsonl')
  GROUP BY ALL ORDER BY n DESC
""").show()

# Attach the app database (read-only) and join across sources
con.sql("ATTACH 'data/raw/qafila_oltp.sqlite' AS app (TYPE sqlite, READ_ONLY)")
con.sql("""
  SELECT s.city, count(*) AS orders
  FROM app.orders o JOIN app.stores s USING (store_id)
  GROUP BY ALL
""").df()                         # → pandas; .pl() → Polars
In-process: pip install duckdb. No server, no cluster.
Columnar + vectorized: scans millions of rows per second per core.
Reads everything: CSV, JSON, Parquet, Iceberg, SQLite, PostgreSQL, S3/HTTP.
Larger than memory: spills to disk; handles tens of GB on a laptop.
Profiling a new source

Before you build anything, look at the data

  • Shape: rows, columns, types. Does the type match the meaning?

  • Freshness and volume: latest timestamp, rows per day.

Files & columnar storage

02
Layout matters

Row storage vs. column storage

Row-oriented: each record stored together

5001 · RUH-01 · 84.5 · delivered5002 · JED-02 · 31.0 · cancelled5003 · RUH-01 · 12.0 · delivered

Column-oriented: each column stored together

5001 · 5002 · 5003RUH-01 · JED-02 · RUH-0184.5 · 31.0 · 12.0delivered · cancelled · delivered
Read only what you need: SUM(amount) touches one column out of thirty.
Compresses well: similar values sit next to each other (RUH-01, RUH-01, …).
Vectorized: CPUs process a column chunk in tight loops (SIMD).
Trade-off: single-row inserts and updates are expensive, so batch your writes.

Inside a Parquet file

Row groups, column chunks, pages and a footer

  • Row group: a horizontal slice (DuckDB: 122,880 rows; Spark: ~128 MB). The unit of parallelism and skipping.
  • Column chunk: one column inside a row group, split into pages.
  • Footer: read first. It holds the schema and the statistics engines use to skip data.
  • Encodings: dictionary (repeated strings), run-length, delta (sorted ints, timestamps).
  • Compression on top: Snappy (fast), ZSTD (smaller; a good default today).
Pushdown

The fastest data is the data you never read

-- Projection pushdown: read 2 of 9 columns
-- Predicate pushdown: skip row groups whose
--   max(created_at) < '2026-09-23'
EXPLAIN ANALYZE
SELECT store_id, sum(amount)
FROM 'orders.parquet'
WHERE created_at >= '2026-09-23'
GROUP BY store_id;

-- Inspect what the engine can use to skip
SELECT row_group_id, path_in_schema,
       stats_min, stats_max, compression
FROM parquet_metadata('orders.parquet');
Projection pushdown: only the referenced columns are decoded. SELECT * defeats it.
Predicate pushdown: row groups whose min/max cannot match are skipped entirely.
Sort to skip: statistics only help if values are clustered. Sorting by created_at before writing makes date filters skip almost everything.
Partitioning

Directories as a coarse index

orders/
  order_date=2026-09-22/part-0.parquet
  order_date=2026-09-23/part-0.parquet
  order_date=2026-09-24/part-0.parquet
  ...
con.sql("""
  COPY (SELECT *, created_at::DATE AS order_date
        FROM orders)
  TO 'lake/orders' (FORMAT parquet,
                    PARTITION_BY (order_date))
""")
# a filter on order_date opens one folder
con.sql("""SELECT count(*) FROM read_parquet(
  'lake/orders/*/*.parquet', hive_partitioning=true)
  WHERE order_date = '2026-09-23'""")
Good partition keys are low-cardinality and match how data is filtered and loaded: date, country, tenant.
Over-partitioning (by customer, by hour for small tables) creates thousands of tiny files: listing and opening them costs more than reading the data.
The small-files problem

Many tiny files are slow, expensive and fragile

1 × 1 GB file
fast
100 × 10 MB files
ok
10,000 × 100 KB files
slow

Same data, illustrative relative read time: each file costs a request, a footer read and planning work.

  • Typical targets: files of 128 MB – 1 GB, row groups of ~128 MB.
  • Streaming and frequent micro-batches create small files by design (Day 3).
  • Fix with compaction: periodically rewrite small files into big ones. Table formats make that safe for concurrent readers.

Session 3

Batch ingestion

  • Choose between full and incremental extraction; track a high-water mark
  • Pull from APIs reliably: pagination, rate limits, retries
  • Make loads idempotent and survive schema changes, with dlt
03
Where data comes from

Every source type has its own failure modes

Databases

Load on production, long-running queries, deletes you can't see, time zones in timestamps.

APIs

Pagination, rate limits, tokens that expire, fields that appear or disappear.

Files

Late or partial uploads, encodings, delimiters, renamed columns, re-sent files.

Events

Duplicates, out-of-order and late arrival, schema per producer version (Day 3).

Talk to the source owner first: what changes, how often, how deletes are represented, what the keys are, and who to call when it breaks. That conversation is the first draft of a data contract (Day 4).
Extraction strategies

Full vs. incremental

Full extract

Copy everything, every time. Simple and always correct, including deletes. Fine for small tables (stores, products).

Incremental extract

Copy only what changed since the last run, using a cursor (high-water mark) like updated_at or an increasing ID.

-- state from the previous run: last_value = '2026-09-29 23:58:10'
SELECT *
FROM orders
WHERE updated_at > :last_value      -- strictly greater?
ORDER BY updated_at;
-- after a successful load, store the new max(updated_at)
Cursor traps: rows with the same timestamp split across runs (use >= + dedupe), clock skew, updates that don't touch updated_at, and hard deletes, which no cursor can see (CDC fixes this, Session 4).
APIs in practice

Pagination, rate limits and retries

import random, time, requests

def get_with_retry(url, params, tries=6):
    for attempt in range(tries):
        r = requests.get(url, params=params, timeout=30)
        if r.status_code == 429 or r.status_code >= 500:
            wait = float(r.headers.get("Retry-After", 0)) \
                   or min(60, 2 ** attempt) + random.random()
            time.sleep(wait)          # exponential backoff + jitter
            continue
        r.raise_for_status()          # 4xx: a bug, don't retry
        return r.json()
    raise RuntimeError(f"gave up after {tries} tries")

page, rows = 1, []
while page:
    body = get_with_retry(f"{BASE}/payments",
                          {"updated_since": cursor, "page": page})
    rows += body["data"]
    page = body["next_page"]
Pagination: offset/page numbers drift if data changes during the read; cursor tokens are safer.
Rate limits: honour 429 + Retry-After. Back off exponentially, add jitter so workers don't retry in lockstep.
Retry only what is retryable: timeouts, 429, 5xx. A 400 or 401 will fail again.
Secrets: tokens come from a secret store or env vars, never from code or notebooks.
The most important property

Idempotency: running twice = running once

Pipelines will be re-run: retries, backfills, a colleague pressing "run" again. If a re-run creates duplicates, every number downstream is wrong.

TechniqueUse when
Merge / upsert on a keyrecords have a stable primary key
Replace a partitionloads are per day/hour (delete + insert that slice)
Replace the tablesmall dimensions, full extracts
Dedupe on readappend-only raw layer; latest record wins
Not idempotent: INSERT INTO raw SELECT * FROM api_page on every run.
Idempotent: MERGE INTO payments USING batch ON payment_id …, or "delete load_date = today, then insert".
Atomic state: save the new cursor after the data commits. Saving it first loses data when the load fails halfway.

A tool for this

dlt: ingestion as a Python library

import dlt
from dlt.sources.helpers.rest_client import RESTClient
from dlt.sources.helpers.rest_client.paginators import JSONResponsePaginator

@dlt.resource(primary_key="payment_id", write_disposition="merge")
def payments(updated=dlt.sources.incremental(
        "updated_at", initial_value="2026-08-01T00:00:00Z")):
    client = RESTClient(base_url=API,
        paginator=JSONResponsePaginator(next_url_path="next"))
    for page in client.paginate("/payments",
            params={"updated_since": updated.last_value}):
        yield page

pipe = dlt.pipeline("qafila", destination="duckdb",
                    dataset_name="raw")
info = pipe.run(payments())
print(info)   # load id, tables, rows; state saved in the destination
Incremental state: the cursor is stored with the data and committed with it.
Write dispositions: append, replace, merge (on primary_key).
Schema inference + evolution: new fields become new columns; nested JSON becomes child tables.
Load metadata: every row gets _dlt_load_id; every run is recorded in _dlt_loads.

Open source (Apache 2.0). Managed alternatives such as Fivetran or Airbyte do the same job with prebuilt connectors.

Capturing change

Three ways to know what changed

ApproachHowSees deletes?Source loadLatency
Snapshot difffull copy, compare with last copyyeshighhours
Query-basedWHERE updated_at > cursorno (soft deletes only)mediumminutes

Log-based CDC (e.g. Debezium on PostgreSQL logical replication or the MySQL binlog) emits every insert, update and delete, in commit order, without querying the tables.
Common path: DB log → Debezium → Kafka → sink (lakehouse table or warehouse). Managed: Fivetran, AWS DMS, Datastream, Confluent connectors.
Anatomy of a change event

Before, after, operation, position

{
  "op": "u",
  "before": {"customer_id": 104063, "city": "Jeddah",
             "district": "Obhur", "mobile": "0541622064", "...": "..."},
  "after":  {"customer_id": 104063, "city": "Riyadh",
             "district": "Hittin", "mobile": "0541622064", "...": "..."},
  "source": {"db": "qafila", "table": "customers",
             "lsn": 5012874},
  "ts_ms": 1758802245000
}
op: c create, u update, d delete (r = snapshot read).
before / after: full row images. A delete has only before.
lsn: log sequence number: the true order of changes. Arrival order is not.
Delivery is at-least-once: expect duplicates after a connector restart.
Applying changes

Dedupe, keep the latest per key, then MERGE

WITH changes AS (
  SELECT DISTINCT ON (source.lsn) *              -- 1 · drop redelivered duplicates
  FROM read_json_auto('data/raw/cdc/customers_changes.jsonl')
), latest AS (
  SELECT coalesce(after.customer_id, before.customer_id) AS customer_id, op, after
  FROM changes
  QUALIFY row_number() OVER (PARTITION BY coalesce(after.customer_id, before.customer_id)
                             ORDER BY source.lsn DESC) = 1   -- 2 · last change per key wins
)
MERGE INTO customers AS t
USING latest AS s ON t.customer_id = s.customer_id
WHEN MATCHED AND s.op = 'd' THEN DELETE                       -- 3 · hard delete
WHEN MATCHED THEN UPDATE SET city = s.after.city, district = s.after.district,
                             mobile = s.after.mobile, updated_at = s.after.updated_at
WHEN NOT MATCHED AND s.op <> 'd' THEN INSERT (customer_id, city, district, mobile, updated_at)
  VALUES (s.customer_id, s.after.city, s.after.district, s.after.mobile, s.after.updated_at);
MERGE is standard SQL (DuckDB ≥ 1.4, Spark/Delta, Iceberg, Snowflake, BigQuery). Ordering by lsn, not by arrival, is what makes out-of-order delivery harmless.
The INSERT branch is simplified on the slide; in the lab the column list is explicit. DISTINCT ON keeps one row per lsn: a redelivered event is identical, so it doesn't matter which copy survives.
Deletes

Hard, soft, and tombstones

Hard delete

Row disappears from the source. Invisible to cursors; CDC emits op = d. Required for erasure requests under PDPL.

Soft delete

Source sets is_deleted = 1 (an update). Easy to replicate, but every consumer must filter it.

Tombstone

In Kafka, a message with a key and a null value: "forget this key" for compacted topics.

Decide explicitly how each layer represents deletes. A common choice: bronze keeps every event; silver applies hard deletes; marts exclude soft-deleted rows. Personal data must really disappear from every layer and every snapshot (Day 4).
