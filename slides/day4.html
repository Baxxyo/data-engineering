01
Beyond cron

What an orchestrator gives you

Order

Run steps in dependency order, in parallel where possible. No more "the 02:00 job finished at 02:40, the 02:30 job read half-written data".

Recovery

Retries with back-off, re-run from the failed step, backfills of past dates.

Triggers

Schedules, sensors (a file landed, an upstream table changed), manual runs.

Visibility

Run history, logs, lineage graph, how long each step takes, what's stale.

Alerting

Failures and failed checks go to the owner: Slack, email, on-call.

Configuration

Same code in dev, staging and prod with different resources and secrets.

Two mental models

Tasks vs. assets

Task-based (Airflow 2 style)

extract >> load >> transform >> publish

The orchestrator knows steps ran. Which tables they produced, and whether those are fresh, lives in your head.

Asset-based (Dagster, Airflow 3 assets)

@dg.asset(deps=[raw_orders])
def fct_orders(): ...

The orchestrator knows data: what each table depends on, when it was last built, whether its checks passed.

"Rebuild everything downstream of the courier events" becomes one selection instead of a hand-maintained task list (Lab 4.1, Task 2).

Partitions and backfills

One partition per day, and every run is idempotent

DAYS = dg.DailyPartitionsDefinition(start_date="2026-09-24")

@dg.asset(partitions_def=DAYS)
def delivery_events_daily(context):
    day = context.partition_key
    sql("DELETE FROM ops.delivery_events_daily "
        "WHERE day = $day", {"day": day})
    sql(f"INSERT INTO ops.delivery_events_daily "
        f"{LOAD_SQL}", {"day": day})
Delete-then-insert per partition (or MERGE, or partition overwrite) makes a re-run produce the same table. Lab 4.1: 22,518 rows after the backfill, 22,518 after re-running Sep 27.
An append-only partition doubles its rows on every retry. Backfills and retries are normal operations: design for them.
Partition by the date the data arrived for loads (yesterday's file), by event date for analytics.
Asset checks

Blocking checks stop bad data from spreading

@dg.asset_check(asset=delivery_events_daily,
                blocking=True)
def no_duplicate_events(context):
    dupes = sql("SELECT count(*) - count(DISTINCT event_id) "
                "FROM ops.delivery_events_daily "
                "WHERE day = $day", {"day": day})[0][0]
    return dg.AssetCheckResult(
        passed=dupes == 0, metadata={"duplicates": dupes})
First backfill: every day fails the check (312 duplicate events across 7 days), so daily_delivery_kpis is skipped, not computed from bad data.
Fix the load (keep one row per event_id), backfill again: all 7 partitions pass.
Blocking when downstream damage is expensive (finance, customer-facing); warn when a human should look but the data is still useful.

02
Data observability

Five things to watch on every important table

Freshness

When did it last change? Is that later than promised?

Volume

Did today's load bring roughly the expected number of rows?

Schema

Columns added, removed, renamed, retyped.

Distribution

Null rates, value ranges, category mix drifting.

Lineage

What feeds this table, and who reads it? Who must be told?

+ Cost

FinOps: which models and queries burn the budget? Track it like any other metric.

Tests check what you expect. Monitors catch what you didn't think to test. You need both. Tools: Elementary, Soda, Monte Carlo, Datadog, plus orchestrator freshness checks and OpenLineage for cross-tool lineage.
Monitors that people don't mute

A naive volume monitor cries wolf every weekend

Baseline for "expected orders"Alerts in Aug–Sep
median of the previous 7 days, ±20%16: 14 of them ordinary Thursdays and Fridays (+25% peaks)
median of the same weekday over 4 weeks, ±30%2: National Day (+102%, on the calendar) and Sep 29 (−57%, the incident)
A monitor that alerts every week gets muted, and then misses the real incident.
Model seasonality (weekday, Ramadan, month-end), keep a calendar of planned events, and route alerts to the table's owner.
Data contracts

An agreement between producer and consumers, in code

  • Schema: fields, types, keys, required, unique.
  • Semantics: what each field means, units, what's excluded.
  • Quality rules: row counts, valid values, custom SQL.
  • Service levels: latency, frequency, retention, support hours.
  • People: owner, consumers, support channel; classification of sensitive fields.
Open Data Contract Standard (ODCS, Bitol project, Linux Foundation AI & Data): one vendor-neutral YAML format. v3.1 is the current release; v3.2 is in development.
Contracts sit at team boundaries: a provider's feed, a domain's published tables, a mart other teams build on. Not every staging model needs one.
ODCS in practice

The payments feed contract (excerpt)

apiVersion: v3.1.0
kind: DataContract
team:
  - {username: payments-provider-integration, role: owner}
schema:
  - name: payments
    quality:
      - type: sql
        query: SELECT count(*) FROM {object} WHERE amount <= 0
        mustBe: 0
    properties:
      - name: status
        required: true
        quality:
          - metric: invalidValues
            arguments: {validValues: [captured, failed, refunded]}
            mustBe: 0
slaProperties:
  - {property: latency, value: 1, unit: d}
Lab 4.2: 26 of 27 checks pass. The contract finds 16 payments with amount ≤ 0: now it's a breach with an owner and a support channel, not "weird data".
The same file generates dbt tests (Lab 4.2 ✱) and orchestrator checks (capstone/pipeline.py). Tooling: the datacontract CLI.
Change management

Breaking or not?

Change (from the consumer's side)Breaking?Why
Column removed or renamed (amount → amount_sar)✗ yesqueries fail
Type changed (card_last4 string → integer)✗ yesleading zeros lost, joins and casts break
New allowed value (status = 'chargeback')✗ yesconsumers' CASE logic silently mishandles it
Required field becomes optional✗ yesunexpected nulls
New column; optional field becomes required; fewer allowed values✓ noexisting queries keep working
Breaking → new major version, published next to the old one with a migration window. Run the contract diff in the producer's CI; use lineage to list who must migrate (Lab 4.2: 4 models and 7 tests read raw.payments).

The Saudi context

PDPL and NDMO, from a data engineer's seat

PDPL (Personal Data Protection Law, enforced since September 2024; SDAIA is the competent authority): lawful purpose, data minimization, data subjects' rights (access, correction, erasure), breach notification, conditions on transfers outside the Kingdom.
NDMO data management and personal data protection standards: governance roles, data catalog, quality, and classification in four levels: Top Secret, Secret, Restricted, Public.
RequirementPipeline feature
Know what you holdPII discovery, catalog tags
Minimize, limit accessmasked views, role grants, pseudonyms
Erase on requestdeletes + snapshot expiry + orphan cleanup
Keep data in the Kingdomstorage region, backups, LLM endpoints
Show compliancelineage, access logs, retention jobs

Engineering view only, not legal advice: your organization's DPO and policies decide classifications and retention.

Discovery

Find personal data by content, then confirm with checksums

def is_saudi_id(s):            # national ID / Iqama
    if not (len(s) == 10 and s.isdigit()
            and s[0] in "12"):   # 1 citizen, 2 resident
        return False
    total = 0
    for i, ch in enumerate(reversed(s)):
        d = int(ch) * (2 if i % 2 else 1)
        total += d - 9 if d > 9 else d
    return total % 10 == 0       # Luhn

def is_saudi_iban(s):          # SA + 22, ISO 13616
    r = s[4:] + s[:4]
    return int("".join(str(int(c, 36))
               for c in r)) % 97 == 1
Column names lie (notes, ref, extra_1). Lab 4.3 finds national IDs, IBANs, mobiles and emails hiding in free-text support notes.
A regex finds 83 ten-digit candidates in the notes; the Luhn check keeps 77 real IDs and drops the tracking numbers.
Some PII has no pattern (names, addresses): declare it in the catalog.
Protection techniques

Mask, pseudonymize, anonymize, encrypt

TechniqueExampleReversible?Still personal data?
Masking+9665•••••24, a•••@gmail.comno (for the viewer)the base table is
PseudonymizationHMAC-SHA256(national ID, secret key)by whoever holds the keyyes
Anonymizationaggregates, k-anonymity, differential privacynono, if done properly (hard!)

Plain hashing isn't pseudonymization. Lab 4.3: an attacker with 500 leaked IDs re-identifies all 500 from unsalted SHA-256 hashes; with HMAC and no key, zero.
HMAC tokens still let analysts find the 58 people with two accounts, without seeing a single ID.
Access control

Each role sees only what it needs

CREATE VIEW analyst.customers AS
SELECT pseudo(national_id) AS person_token,
       customer_id, city, district,
       lower(split_part(email, '@', 2))
           AS email_domain,
       created_at
FROM main.customers;

CREATE VIEW support.customers AS
SELECT customer_id, full_name, email,
       mask_mobile(mobile) AS mobile, city
FROM main.customers;
RBAC: roles get grants on schemas/views, never on raw PII tables.
Policies in the platform: column masks and row filters (Snowflake, BigQuery, Unity Catalog) apply in every tool, not just one view.
Tag-based: classify once (Secret), and the policy follows the tag to every table.

DELETE is only step one

1 · Deletenew snapshot without the row
→

→

Also: derived tables and incremental models, backups, partner exports, column stats in old manifests. At scale: batch erasures weekly, or crypto-shredding (per-person keys, delete the key).
