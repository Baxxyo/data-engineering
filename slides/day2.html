01
Under the hood

Four ideas behind every fast analytical engine

Columnar

Data in memory is laid out by column (Apache Arrow), like Parquet on disk. Scans touch only needed columns.

Vectorized

Operators process batches of ~2,000 values at once instead of one row at a time: CPU caches and SIMD stay busy.

Parallel

Morsel-driven: work is split into small chunks spread across all cores automatically.

Optimized

Queries become plans that are rewritten before running: pushdowns, join reordering, pruning.

DuckDB, Polars, DataFusion, ClickHouse, Snowflake, Spark's Photon, BigQuery: different products, same four ideas. Learn them once.

One question, two interfaces

SQL and DataFrames are the same plan

SELECT o.store_id,
       round(sum(i.quantity * i.unit_price
                 - i.discount), 2) AS revenue
FROM raw.orders o
JOIN raw.order_items i USING (order_id)
WHERE o.status = 'delivered'
  AND o.created_at >= '2026-09-01'
GROUP BY o.store_id
ORDER BY o.store_id;
(orders
 .filter((pl.col("status") == "delivered")
         & (pl.col("created_at") >= "2026-09-01"))
 .join(items, on="order_id")
 .group_by("store_id")
 .agg((pl.col("quantity") * pl.col("unit_price")
       - pl.col("discount")).sum().round(2)
       .alias("revenue"))
 .sort("store_id")
 .collect())
SQL for relational logic that analysts review and dbt manages: most of a warehouse.
DataFrames for procedural or parametrized logic, and code you unit-test as Python functions. Both exchange data through Arrow for free.

Time is hard

Store UTC, convert at the edge

  • Store and compute in UTC; convert to Asia/Riyadh for business days and display.
  • Riyadh is UTC+3 all year (no daylight saving), but your partners and your cloud region may not be.
  • An order at 22:30 UTC on 22 Sep is a 23 Sep order in Riyadh: date boundaries move revenue between days.
  • Two clocks for every event: event time (when it happened) and ingest time (when we got it). Keep both.
et = pl.col("event_time")
events = events.with_columns(
  pl.when(et.str.contains(r"^\d{13}$"))      # epoch ms
    .then(pl.from_epoch(et.cast(pl.Int64),
                        time_unit="ms")
            .dt.replace_time_zone("UTC"))
    .otherwise(et.str.to_datetime(           # ISO +03:00 / Z
                 time_zone="UTC"))
    .alias("event_at_utc"))
events.with_columns(
  pl.col("event_at_utc")
    .dt.convert_time_zone("Asia/Riyadh"))

02
Why model at all?

Data modeling is the industry's sore spot

59%
name "pressure to move fast" as their top modeling pain
11%
say data modeling is going well in their organization
≈5%
use semantic models

Source: Joe Reis, 2026 State of Data Engineering survey (≈1,100 data practitioners).

Without a model, every analyst re-joins raw tables their own way, and "revenue" has five definitions. A dimensional model is a shared, documented answer to "what happened, to whom, where, when".
Facts and dimensions

The star schema

Fact: one row per business event (an order line), with measures you add up and keys to context.
Dimension: descriptive context you filter and group by: when, what, where, who.
Why it works: every question is "filter dims, group by dims, sum facts". Simple for people, fast for engines.
Kimball's four steps

Grain first, everything else follows

  1. Business process: customers place orders (not "the orders table").
  2. Grain: one row per order line. Write it down; test it (unique key).
  3. Dimensions: whatever is single-valued at that grain: date, product, store, customer, promotion.
  4. Facts: numbers measured at that grain: quantity, unit price, discount, net amount.
Grain mismatch is the root of most wrong numbers. The delivery fee is per order: it can't live in a per-line fact. It goes in fct_orders.
Three kinds of fact tables

Transactions, snapshots, accumulating snapshots

TypeGrainQafila exampleAdditive over time?
Transactionone row per eventfct_order_items, paymentsyes
Periodic snapshotone row per entity per periodstock on hand per product per store per dayno (stock isn't summed over days)
Accumulating snapshotone row per process instance, updated as it movesfct_orders with placed → assigned → picked → delivered timespartly
Semi-additive measures (balances, stock levels) can be summed across stores but not across days: average or take the last value instead.
Keys

Surrogate keys and the unknown member

Natural key: the source's ID (product_id, national_id). Can be reused, reformatted, or clash between sources.
Surrogate key: an integer owned by the warehouse. Required when a dimension keeps history (SCD2 has several rows per customer) or merges sources.
Unknown member (-1): facts whose reference is missing still join. Inner joins no longer silently drop revenue.
-- lines of erased customers keep their revenue
SELECT ...,
  coalesce(c.customer_key, -1) AS customer_key
FROM order_items i
JOIN orders o USING (order_id)
LEFT JOIN dim_customer c
  ON c.customer_id = o.customer_id;

-- in Lab 2.2: 3,930 lines → customer_key = -1

Star, snowflake, one big table, Data Vault

StyleShapeGood forWatch out

The classic mistake

Fan-out: joining a coarse grain to a fine one

-- ✗ the fee is repeated once per order LINE
SELECT sum(f.net_amount + o.delivery_fee)
FROM fct_order_items f
JOIN orders o USING (order_id);

-- ✓ sum each measure at its own grain
SELECT (SELECT sum(net_amount)
        FROM fct_order_items)
     + (SELECT sum(delivery_fee)
        FROM fct_orders) AS revenue_incl_fees;
In Lab 2.2 the naive query overstates Qafila's revenue by about 1 million SAR (≈14%): an order with 4 lines pays its 9 SAR fee 4 times.
Combine facts at a shared grain (per order, per day), never by joining one fact's rows to another's. Watch payments per order and events per order too.

dbt: transformation as software

  • Structure a project into staging, intermediate and marts
  • Use sources, refs and materializations, including incremental models

03
What dbt does

You write SELECTs. dbt does everything around them.

  • Each model is one SQL file with one SELECT; dbt wraps it in CREATE VIEW/TABLE AS.
  • ref() and source() build a dependency graph: dbt runs models in order, in parallel where possible.
  • Jinja templating: variables, loops, macros (reusable SQL functions).
  • YAML next to the SQL: docs, tests, contracts.
  • The engine is your warehouse: DuckDB, Snowflake, BigQuery, Databricks, Postgres… dbt only sends SQL.
dbt_project.yml        # name, folder configs, vars
profiles.yml           # connection (DuckDB file)
macros/text.sql        # normalize_arabic, to_riyadh, ...

Incremental models

Process what changed, with a look-back window

{{ config(
    materialized='incremental',
    unique_key='order_line_id',
    incremental_strategy='delete+insert',
    on_schema_change='fail') }}

with orders as (
  select * from {{ ref('stg_orders') }}
  {% if is_incremental() %}
  where updated_at_utc >
    (select max(order_updated_at_utc)
            - interval 3 day
     from {{ this }})
  {% endif %}
)
select ... from orders join ...
is_incremental(): true when the table exists and you didn't pass --full-refresh.
{{ this }}: the existing table. Its max timestamp is your high-water mark.
unique_key + delete+insert / merge: reprocessed rows replace old ones; no duplicates.
Look-back (3 days): catches late changes such as refunds. Size it from how late your data really is.
Macros

Write a rule once, use it everywhere

{% macro to_riyadh(ts) -%}
    ({{ ts }} + INTERVAL 3 HOUR)
{%- endmacro %}

{% macro normalize_ksa_mobile(col) -%}
  CASE WHEN regexp_full_match(
         regexp_replace({{ col }}, '[^0-9]', '', 'g'),
         '(966|0)?5\d{8}')
       THEN '+966' || right(
         regexp_replace({{ col }}, '[^0-9]', '', 'g'), 9)
  END
{%- endmacro %}

dbt in 2026

One project format, two engines

dbt v1 (Python)

The engine formerly called dbt Core, used in our labs (dbt-core 1.12 + dbt-duckdb). Open source, runs anywhere Python runs.

dbt v2 (Rust, formerly "Fusion")

Generally available since September 2026. Much faster parsing, and it understands SQL: column-level lineage and errors caught before anything runs.

  • dbt Labs and Fivetran merged in 2026: ingestion and transformation under one roof.
  • An Apache 2.0 open-source distribution remains; some features of the full distribution are under a separate license. Check licensing for your use.
  • Alternatives with the same "SQL as software" idea: SQLMesh, Dataform (BigQuery), Spark SQL pipelines.
  • What carries over: models, refs, tests, layering. Your skills don't depend on the engine.
Facts from dbt Labs' and Fivetran's announcements (merger closed June 2026; dbt v2 GA at dbt Summit, September 2026). Keep the licensing point light; tell participants to check the current licence FAQ before choosing.

What "quality" means

Six dimensions, each with a test

Uniqueness: one row per key
unique(order_line_id)
Completeness: required values present
not_null(event_at_utc)
Validity: values in the allowed set/range
accepted_values(status), positive(quantity)
Consistency: references and totals agree
relationships, payments = order totals
Timeliness: data is fresh enough
dbt source freshness (Day 4)
Accuracy: data matches reality
reconciliation with the source (Lab 1.4)

Day 4
Each layer catches what the others can't: a unit test can't know the supplier renamed a column; a data test can't tell you which code path is wrong.
Data tests in dbt

Declare expectations next to the model

- name: stg_orders
  columns:
    - name: order_id
      data_tests: [unique, not_null]
    - name: status
      data_tests:
        - accepted_values:
            arguments:
              values: [placed, delivered, cancelled,
                       refunded, failed_delivery]
    - name: customer_id
      data_tests:
        - relationships:
            arguments:
              to: ref('stg_customers')
              field: customer_id
            config:
              severity: warn    # 1,040 erased customers
Generic tests: unique, not_null, accepted_values, relationships, plus your own (tests/generic/positive.sql).
Singular tests: any SQL in tests/ that returns the bad rows (payments vs. order totals).
A test passes when it returns zero rows. Under the hood it's just a query, so you can run it by hand.
When a test fails

Error, warn, or quarantine?

Error

Stop: downstream models are skipped. For problems that make data wrong: broken grain, a fact without its dimension.

Warn

Continue, but tell someone. For known, tolerated issues: orphan orders after erasure. Every warning needs an owner.

Quarantine

Route bad rows to a side table with the reason; publish the rest. For row-level problems: negative quantities, bad supplier costs.

select *, 'non-positive quantity' as reject_reason
from {{ ref('stg_order_items') }}
where quantity <= 0          -- and fct_order_items keeps "where quantity > 0"
Contracts and unit tests

Guard the shape; test the logic

- name: fct_order_items
  config:
    contract:
      enforced: true
  columns:
    - name: order_line_id
      data_type: bigint
      constraints: [{type: not_null}]
    - name: quantity
      data_type: bigint
    # ... every column, name + type
unit_tests:
  - name: test_supplier_costs_are_parsed
    model: stg_supplier_prices
    given:
      - input: source('raw', 'supplier_prices')
        rows:
          - {sku: QF-2, unit_cost: "9,49"}
          - {sku: QF-3, unit_cost: "٩٫٤٩"}
    expect:
      rows:
        - {sku: QF-2, unit_cost_sar: 9.49}
        - {sku: QF-3, unit_cost_sar: 9.49}
Contract: checked before the table is replaced. A type change fails the build instead of breaking dashboards.
Unit test: fixed inputs, expected outputs, no real data needed. Cheap: put one on every tricky rule.
Validation at the door

Pandera: a schema for DataFrames

import pandera.polars as pa

class SupplierPrice(pa.DataFrameModel):
    supplier_id: str = pa.Field(str_startswith="SUP-")
    sku: str = pa.Field(isin=known_skus)
    unit_cost_sar: float = pa.Field(gt=0)
    currency: str = pa.Field(isin=["SAR"])
    min_order_qty: int = pa.Field(isin=[6, 12, 24, 48])

try:
    SupplierPrice.validate(prices, lazy=True)
except pa.errors.SchemaErrors as e:
    failures = e.failure_cases   # one row per failure
    # → quarantine those rows, load the rest,
    #   send the list back to the supplier
lazy=True collects every failure instead of stopping at the first: one report to send back.
Works on pandas, Polars and PySpark DataFrames. Alternatives: Great Expectations, Soda, dlt schema contracts.

Tests in CI

Run the tests before the merge, not after the incident

on: pull_request
jobs:
  dbt:
    steps:
      - uses: actions/checkout@v4
      - run: uv sync
      - run: dbt deps
      # only what changed, plus everything downstream,
      # compared with production's manifest
      - run: dbt build --select state:modified+
               --defer --state prod-artifacts/
  • Slim CI: build only modified models and their children; defer unchanged parents to production.
  • Separate dev / CI / prod targets: a PR never writes to production schemas.
  • Block the merge when an error test fails; post warnings as a PR comment.
  • Review SQL like code: the reviewer reads target/compiled, not just the Jinja.
